## 4. План

Шесть фаз. A — дни, остальные — недели; D и F идут параллельно с B–E.
Каждая фаза заканчивается проверяемым критерием, а не списком задач.

### Фаза A. Остановить кровотечение — неделя 1

Ничего нового. Только то, что мешает выпускать.

1. **Закоммитить 232 файла** отдельными коммитами по подсистемам (ядро, ИИ, CRM, тесты), запушить.
2. **`APP_DEBUG=false`** на экземпляре, доступном снаружи. Проверить, что ошибка 500 отдаёт страницу без трассировки.
3. **Службы вместо ручных процессов:** php-cgi с `PHP_FCGI_MAX_REQUESTS=0`, `queue:work`, `schedule:work` — через nssm с автоперезапуском. Или VPS с php-fpm по конфигу из `deploy/nginx/`; виртуальный хостинг ps.kz закрыт требованием PHP 8.4.1.
4. **Логотипы:** два PNG по 1,2 МБ → WebP через уже написанную `media:variants` и `<x-picture>`. Ожидание: мобильный LCP с 16 с до < 4 с одним этим шагом.
5. **Гонка `form_token`:** второй POST должен получать тот же ответ, что первый, а не 500. Тест на два параллельных запроса уже написан в аудите — довести до зелёного.

**Состояние на 5 ноября:** п. 1 — работа закоммичена и запушена (отчёт аудита хранится локально); п. 2 — `APP_DEBUG=false`; п. 4 — логотипы WebP 640 px (23 и 52 КБ), скрытый темой логотип не скачивается; п. 5 — гонка `form_token` закрыта, тест в `CartTest`; чек-листы раздела 22 спецификации сверены с кодом. Открыт п. 3: в тот же день пул php-cgi завис и был перезапущен вручную — службы с автоперезапуском нужны в первую очередь. LCP после сжатия логотипов ещё не перемерен.

Критерий: `nginx -t`, три службы в `services.msc` со статусом Running после перезагрузки машины, Lighthouse mobile LCP < 4 с, тест гонки зелёный, `git status` чист.

### Фаза B. Розничный выпуск — недели 2–5 (этап 3 спецификации)

Цель: гость оформляет заказ через новое ядро, а не через legacy `CreateOrder`.

1. **Включить `ORDERING_STOREFRONT_CORE`** сначала на preview, прогнать 14 браузерных сценариев, затем на бою. Legacy-путь остаётся за флагом ещё один выпуск для отката.
2. **Вход по коду (SMSC.kz + fake-драйвер).** Сейчас пароль. Спецификация 17.1: код → привязка → история. Пароль сохранить как резервный путь для тех, кто уже завёл кабинет.
3. **Повторение заказа и изменение до подтверждения** — из прототипа `/preview/ux` в рабочий кабинет (раздел 9).
4. **Запрос изменения/отмены после подтверждения** → задача менеджеру в Filament (раздел 9.3).
5. **Липкая шапка на малых экранах** — не перекрывать сфокусированное поле (находка аудита).

Критерий: 100 последовательных гостевых заказов на preview без 500; дубли при повторе callback — 0; OTP не открывает чужую историю (тест); сценарии Playwright зелёные на 360 px.

### Фаза C. Опт в бой — недели 4–8 (этап 4)

1. **Сохраняемый черновик для `/opt`** вместо состояния в Livewire — перезагрузка ничего не теряет.
2. **CSV/XLSX в рабочий опт** по модели bird-ie: построчная проверка, понятные ошибки на строке, сохранение шаблона. Код прототипа есть в `app/Livewire/Preview/`.
3. **Наличие по конкретному предложению**, а не по товару: `stock = 0` у выбранного предложения — «под заказ», не «в наличии».
4. **Предложения менеджера и принятие клиентом** — связка уже построена для ИИ-пути (журнал 23.10), подключить к обычному опту.
5. **Импорт прайса и сборка каталога — в очередь `imports`.** Сейчас из HTTP-запроса панели с таймаутом 300 с.

Критерий: оптовик загружает файл на 500 строк, видит ошибки построчно, сохраняет шаблон, повторяет через неделю; менеджер одобряет, клиент принимает — без участия разработчика.

### Фаза D. ИИ для сотрудников — недели 6–10 (новое, в спецификации нет)

Спецификация описывает ИИ только для покупателя. Для сотрудников в CRM есть
просмотр диалогов и утверждённые ответы — и всё. Между тем именно здесь ИИ
окупается быстрее: сотрудник проверяет результат, а не покупатель.

Правило то же, что у покупателя: **ИИ предлагает, человек подтверждает.**
Ничего не меняется в данных без клика сотрудника. Провайдеры те же — Gemini
через существующий `ChatProvider` и локальная модель через LiteLLM.

| Для кого | Что делает | На чём строится |
|---|---|---|
| **Менеджер**, карточка заказа | Сводка диалога покупателя в три строки; черновик ответа клиенту на RU/KK; флаг «применимость не подтверждена» с причиной | `AssistantConversationResource`, `AssistantDialog`, `CheckFitment` — уже есть |
| **Менеджер**, импорт прайса | Для 308 строк «на ручную проверку» — предложение марки и модели с уверенностью; кнопка «принять» | `PriceImportRow.status = review`, `ModelNameAudit` — очередь уже есть, нет подсказки |
| **Контент**, справочник | Сведение двойников: `Toyota "Camry" CV30` и `Toyota Camry CV30` — 505 строк с нераспознанным поставщиком; ИИ предлагает пару, человек сливает | `ModelMerger`, `CarModelAlias` — механика слияния есть |
| **Мастер**, полевая панель | Фото маркировки стекла → еврокод и тип (Gemini vision) → подбор | новое; проверить точность на 50 фото прежде чем показывать мастерам |
| **Владелец** | Еженедельная сводка в Telegram: заказы, воронка, провалы ИИ, задержки очереди | `TelegramClient`, `SalesFunnel`, `RuntimeMetrics` — есть, нет сборки в одно сообщение |

Порядок внутри фазы — по окупаемости: импорт прайса (экономит часы каждый
прайс) → сводка диалога (каждый заказ) → справочник → сводка владельцу →
фото стекла (последнее, требует проверки точности).

Критерий: менеджер разбирает очередь из 308 строк за один сеанс вместо дня;
на 20 реальных заказах черновик ответа принимается без правок хотя бы в
половине случаев — иначе функция отключается, а не остаётся «для галочки».

### Фаза E. Архитектура и эксплуатация — недели 8–12 (этап 6)

1. **Redis** для кеша, сессий, ограничителей и очереди. Сейчас всё в PostgreSQL — работает, но при 300 заказах в день очередь в той же базе, что заказы.
2. **Разделить очереди** по разделу 20.1: `critical` (чеки, платежи), `notifications`, `imports`, `ai`. Сейчас одна `default` плюс `ai`.
3. **Отдельный пул для SSE** ИИ-чата, чтобы ожидание ответа модели не занимало воркеры оформления.
4. **Политики доступа.** Сейчас две (`OrderPolicy`, `UserPolicy`), остальное — проверки в контроллерах. Довести до политик на `Customer`, `Order`, документы, диалоги.
5. **Наблюдаемость** по 20.5: `request_id` в логах, возраст очередей, сигналы в Telegram. `LaunchReadiness` уже проверяет часть — расширить.
6. **Нагрузочный профиль** раздела 20.4 на отдельном стенде: 100 покупателей, 30 минут. Цель p95 поиска ≤ 500 мс. Текущие замеры сняты на временной схеме запуска PHP, а не на целевой архитектуре; мерить заново после фазы A.

Критерий: таблица 20.4 заполнена фактическими числами; каждое нарушение либо устранено, либо записано с причиной.

### Фаза F. Frontend и адаптивность — сквозная

Переделывать нечего: дизайн-система из 73 классов, тёмная тема, нижняя
таб-навигация и бюджеты Lighthouse (`lighthouserc.json`) уже есть. Фаза —
про доведение и измерение.

1. **Core Web Vitals** — после фазы A замерить заново; дальше по месту: `fetchpriority` у LCP-карточки, шрифты только нужных начертаний, казахские символы без скачка метрик.
2. **Казахский — проверка носителем** основных сценариев (21.1). 538 строк переведены машиной; без носителя это не считается готовым.
3. **Доступность по 21.3:** путь покупки с клавиатуры, фокус в модальных окнах, `aria-live` в чате, масштаб 200 %, `prefers-reduced-motion`.

5. **`llms.txt` и MCP к `docs/`** по примеру Lunar — для исполнителей, не для покупателей.

Критерий: Lighthouse mobile p75 LCP ≤ 2,5 с / INP ≤ 200 мс / CLS ≤ 0,1; акт проверки казахского от носителя; 0 находок axe уровня A/AA на пути покупки.

## 5. Чего в плане намеренно нет

- **Переезд на Nuxt, React или Inertia.** Решение 1.1 принято с владельцем, обзор GitHub его подтвердил: ни одна готовая платформа не знает применимость стекла. Переписывание фронтенда — три-четыре месяца без выигрыша для покупателя.
- **Платные провайдеры ИИ.** Запрещены правилами проекта (журнал ИИ, «Ограничения и решения»).
- **Микросервисы, Elasticsearch, отдельный поисковый сервер.** Масштаб — 50 000 предложений и 300 заказов в день; `pg_trgm` с индексами закрывает это (раздел 20.2).
- **Полноценный offline в полевой панели.** Спецификация 20.3 прямо выносит за рамки выпуска.

## 7. Риски, о которых стоит знать заранее

- **Две точки входа в заказ живут одновременно** — legacy `CreateOrder` и новое ядро за флагом. Чем дольше, тем больше правил расходится. Фаза B закрывает это; откладывать её дороже всего.
- **Качество ИИ 85 % при цели 95 %.** Разрыв в 10 пунктов на настоящем провайдере — это каждый седьмой ответ с ошибкой. Автопокупка через чат по умолчанию выключена — и должна оставаться выключенной, пока 200 эталонных диалогов не дадут ≥ 95 %.
- **Единственная копия работы на диске.** Между пушами проходит месяц, а в репозитории нет ни CI, ни автоматических резервных копий базы. Фаза A пункт 1 и фаза E пункт 5.
