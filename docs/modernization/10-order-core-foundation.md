# Этап 2, часть 1 — деньги и постоянные черновики заказа

Дата: 20 сентября 2026 года. Основной план — [MODERNIZATION_SPEC.md](../../MODERNIZATION_SPEC.md).

## 1. Результат и границы

Создан первый рабочий слой общего backend в `app/Domain`: точные денежные значения, правило персональной цены, серверный контекст покупателя, создание/чтение/изменение черновика в PostgreSQL. Черновик принадлежит одному владельцу и имеет версию. Параллельные изменения не перезаписывают друг друга; чтение возвращает согласованные версию и строки.

Это частичное выполнение первого пункта этапа 2. Версия черновика уже реализована, версия расчёта ещё нет. До подключения checkout остаются `CheckoutQuote`, `QuoteDraft`, `SubmitDraft`, идемпотентность, проверка применимости, полный резерв и outbox.

Новые HTTP-маршруты и потребители в Livewire пока не подключены. Сессионные прототипы и действующие формы продолжают использовать прежнюю логику. Новая миграция выполнена и откатана только в отдельной тестовой БД; к рабочей и preview-БД в этой части не применялась.

## 3. Денежные расчёты

### Контракт

- Валюта текущего слоя — только `KZT`.
- `Money::fromDecimal('25000.00')` создаёт `2500000` минимальных единиц.
- Десятичный источник — строка из PostgreSQL `numeric/decimal`; существующие колонки не меняются.
- `fromDecimal()` отклоняет `float`, научную запись, запятую, пробелы, лишние дробные знаки и неоднозначную запись.
- `fromMinor()` принимает только целое число. JSON: `{ "amount_minor": 2500000, "currency": "KZT" }`.
- Поддерживаются сложение, вычитание, умножение на неотрицательное целое количество и скидка в базисных пунктах: 1000 = 10%.
- Абсолютная граница — `9007199254740991` минимальных единиц: целое значение сохраняет точность в JavaScript. Переполнение отклоняется до потери точности.
- Отрицательные значения разрешены для будущих разниц/возвратов; отрицательная или нулевая товарная цена считается неизвестной в `CustomerPriceCalculator`.
- `null` означает неизвестную цену. `Money(0)` остаётся корректным представлением известной бесплатной услуги/доставки, когда это разрешает соответствующее правило.

### Скидка

Округление half-up применяется к цене одной штуки до умножения количества. Пример:

```text
Розница:                   33.35 ₸
Скидка:                       10%
Цена после округления:     30.02 ₸
Три штуки:                 90.06 ₸

Если закуп одной штуки:    30.03 ₸
Цена с учётом минимума:    30.03 ₸
Три штуки:                 90.09 ₸
```

Персональная скидка применяется только при подтверждённом оптовом доступе. Сохраняется действующее ограничение 0–40%. В ответ не возвращается отдельное поле закупочной цены. Неизвестный закуп пока не создаёт самостоятельную проверку готовности: её необходимо определить в `QuoteDraft`; наличие вычисленной цены само по себе не разрешает продажу.

Это правило ещё не заменяет прежние `Offer::sellingPrice()`, `Customer::wholesalePrice()` и `CartQuote`. Их переводить через общий расчёт с регрессиями; не менять формулы по одному контроллеру. Прежнее округление оптовой цены до десятков тенге отличается от согласованного нового правила до двух знаков.

## 4. Владелец и доступ

### Гость

`BuyerContext::guest()` принимает 256-битный токен в виде 64 шестнадцатеричных символов. В таблице хранится SHA-256 токена, сам токен в DTO не попадает. Будущий адаптер должен создать токен через `random_bytes(32)` и хранить его в серверной сессии. Произвольное поле HTTP-запроса не является источником владельца.

Гость может работать только со своим розничным черновиком. Знание UUID чужого черновика или ввод телефона оптовика доступа не даёт.

### Аккаунт

`BuyerContext::account()` получает ID пользователя от аутентифицированного серверного адаптера. Требуются активный пользователь с ролью покупателя и существующая привязка `customer_id`. Сотрудник, отключённый пользователь и аккаунт без привязки не допускаются.

Перед каждой операцией аккаунт и условия опта перечитываются. Отзыв одобрения запрещает новые оптовые черновики и изменение существующего оптового черновика. Собственный черновик остаётся доступен для чтения, пока аккаунт активен. Контактный телефон внутри черновика на доступ и скидку не влияет.

Это ещё не реализация OTP и не новое доказательство владения телефонным номером. Правила настоящего входа и переноса гостевого черновика принадлежат этапу 3. Автоматическое присоединение гостевых данных по совпадению телефона не реализовано.

### База данных

CHECK-ограничение требует ровно одного владельца:

- `customer_id` заполнен, `guest_owner_hash` пуст;
- либо `customer_id` пуст, `guest_owner_hash` заполнен корректным хешем.

Нельзя сохранить запись без владельца или с двумя владельцами. Для аккаунта применяется внешний ключ с запретом удаления связанного покупателя, пока существуют его черновики. Политику очистки/анонимизации добавить отдельно перед выпуском.

Поиск черновика сразу ограничен владельцем. Отсутствующая, чужая и некорректная UUID-ссылка дают одинаковый `RESOURCE_NOT_FOUND`; проверка версии и содержимого выполняется только после проверки доступа.

## 5. Операции черновика

| Операция | Вход | Результат |
|---|---|---|
| `create` | Доверенный `BuyerContext`, режим | Новый UUID, версия 1, статус active |
| `get` | Контекст и UUID | Согласованный снимок заголовка и строк |
| `update` | Контекст, UUID, ожидаемая версия, изменения | Сохранённый черновик с увеличенной версией |

Создание не делает заказ, резерв, оплату или отправку уведомления. Повтор `create` сейчас создаёт новый черновик: идемпотентный вход будет отдельной частью до открытия HTTP API.

### Версии и транзакции

1. Обновление начинает транзакцию и блокирует принадлежащую владельцу запись `FOR UPDATE`.
2. Проверяет актуальный доступ, ожидаемую версию и редактируемый статус.
3. Проверяет входные данные и доступность вновь выбранных предложений.
4. Записывает строки и поля в одной транзакции; версия увеличивается один раз.
5. При устаревшей версии возвращает `DRAFT_VERSION_CONFLICT`, статус 409, `current_version`. Изменения не применяются.

Чтение держит `FOR SHARE` на черновике до загрузки строк. Поэтому между чтением версии и списка товаров другой процесс не может завершить обновление через этот сервис. Заголовок версии 2 не будет выдан со строками версии 3.

Сервис не сливает конкурирующие изменения автоматически. Будущий интерфейс должен перечитать актуальный черновик, сохранить локальную редакцию для сравнения и предложить повторное применение. Самовольный повтор с новой версией может затереть выбор пользователя и не допускается.

Предложения при замене строк читаются одним пакетным запросом с блокировкой в порядке `offer_id`; товары и поставщики загружаются пакетно. Это ограничивает число запросов. Полный порядок блокировок для будущего оформления/резерва ещё предстоит определить и проверить вместе с `SubmitDraft`.

### Разрешённые данные

| Поле | Поведение |
|---|---|
| `items` | Полная замена списка, если поле передано; `[]` очищает список |
| `contacts` | Частичное обновление имени и телефона |
| `vehicle` | Частичное обновление автомобиля, года, VIN и известных опций |
| `fulfillment` | Частичное обновление способа, города, адреса, точки и времени |
| `locale` | RU / KK |

Пропущенные метаданные сохраняются. `null` очищает разрешённое отдельное значение. Пустой объект метаданных ничего не удаляет. Опции автомобиля поддерживают `true`, `false`, `null`: неизвестная камера не превращается в отсутствие камеры.

В одной строке обязательны стабильный UUID `line_id` и целое количество: в рознице 1–20, в опте 1–99. Общий предел хранения — 500 строк. Значения вынесены в `config/ordering.php`; уменьшение лимита действует при следующем обновлении списка. Увеличение сверх физических границ схемы (99 штук / 500 строк) требует отдельной миграции и не принимается молча.

Порог 50 уникальных розничных позиций сохранён в конфигурации для будущего `QuoteDraft`: больший черновик должен направляться менеджеру, а не терять строки. В текущем срезе автоматическое оформление отсутствует. При замене списка клиент передаёт необходимые признаки и комментарий каждой строки полностью: пропущенные подтверждения сбрасываются в `false`, режим подбора — в `vehicle_fitment`, комментарий — в `null`.

Владельца, режим продажи, статус, версию, закуп и цену изменить через `changes` нельзя. Неизвестные ключи отклоняются. Пустая строка вместо массива, integer или boolean отклоняется до обращения к SQL; стандартная проверка необязательных полей Laravel сама по себе могла бы её пропустить.

Контакты и получение здесь допускают незавершённый ввод. Существование автомобиля, согласованность года/модификации, корректность телефона, адреса и слота необходимо проверять на этапе расчёта/отправки. Сохранённый черновик не означает готовый к оплате заказ.

## 6. Строки каталога и удалённые предложения

- Строка с `offer_id` получает артикул, название и производителя из каталога. Цена и название из клиентского payload не принимаются.
- `reference` сохраняет исходный текст клиента или импорта; `article_snapshot` отдельно хранит каталоговый артикул. Их нельзя смешивать при сопоставлении.
- Новое неактивное предложение, предложение скрытого товара или неактивного поставщика не добавляется.
- Уже выбранное предложение после деактивации разрешено оставить в той же строке, чтобы человек мог исправить подбор. Это не разрешение продать его.
- При удалении предложения внешний ключ устанавливает `offer_id = null`. UUID строки, исходный запрос, название, артикул и производитель сохраняются.
- Неразрешённая строка возвращается с `UNRESOLVED_ITEM`. Изменение количества не стирает сохранённый снимок удалённого товара.
- Несколько строк с одним непустым `offer_id` отклоняются как `DUPLICATE_OFFER`; клиент должен явно объединить количество. UUID строк тоже должны быть уникальны без учёта регистра.
- Поле `validation_issues` в этом DTO сообщает только о неразрешённой строке. Полная доступность, применимость, актуальность цены и остатка будут результатом `CheckoutQuote`.

Удаление предложения в каталоге само по себе не увеличивает версию черновика. Поэтому `draft.version` не заменяет версию источников расчёта; перед оформлением обязателен свежий quote и перепроверка фактов.

## 7. Хранение и ошибки

`vehicle`, `contacts`, `fulfillment` используют Laravel encrypted casts и колонки `text`. Их содержимое не лежит в БД открытым JSON. Для чтения после восстановления требуется соответствующий `APP_KEY`; резервное копирование и ротацию ключа включить в эксплуатационный план. Свободный комментарий товарной строки в этом срезе хранится обычным текстом; шифрование трёх полей не означает шифрование всех данных приложения.

DTO содержит разрешённые поля черновика, строки и время обновления в UTC. В нём нет хеша гостя, `customer_id`, закупочной цены и произвольной сериализации модели.

| Код | Статус будущего адаптера | Действие интерфейса |
|---|---|---|
| `AUTH_REQUIRED` | 401 | Восстановить вход |
| `RESOURCE_NOT_FOUND` | 404 | Показать недоступный черновик без сведений о владельце |
| `WHOLESALE_REQUIRED` | 403 | Показать необходимость актуального оптового доступа |
| `DRAFT_VERSION_CONFLICT` | 409 | Получить свежие данные, предложить сравнение |
| `DRAFT_NOT_EDITABLE` | 409 | Открыть состояние завершённого/закрытого черновика |
| `DRAFT_VERSION_LIMIT` | 409 | Не допустить переполнение версии; предложить новый черновик |
| `ValidationException` | 422 | Связать ошибки с конкретными полями/строками |

Это внутренние коды. HTTP/Livewire-адаптер ещё должен привести все ошибки к общему контракту и локализовать сообщения на RU/KK; машинные коды не показывать покупателю как готовый текст интерфейса.

Обновление: расчёт, его версии и проверка условий реализованы в [части 2 этапа 2](11-checkout-quotes.md). Ниже сохранён порядок задач на момент завершения этой части; текущий остаток работ указан в новом отчёте и основном плане.

2. Связать расчёт с конкретными предложениями и актуальным `BuyerContext`; разделить неизвестную цену, нулевую разрешённую стоимость и полную готовность. Добавить согласованные признаки актуальности цены/остатка с безопасными значениями по умолчанию.
3. Реализовать единый fitment и поиск; точный артикул/производитель и подбор по машине должны сохранять разные основания совместимости.
4. До открытия `/api/v1` реализовать хранение идемпотентности, `Idempotency-Key`, fingerprint запроса, область владельца/операции и одновременные повторы. Не выдавать обычный конфликт версии за идемпотентный повтор.
5. Затем реализовать `SubmitDraft`: автоматическая розница при всех проверенных условиях, опт и неопределённые условия — менеджеру; полный атомарный резерв и outbox.
